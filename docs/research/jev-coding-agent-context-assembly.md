## 结论与阅读入口

这篇 PDF 最值得借鉴的地方，是把 **模型这一次需要看到的内容** 从 **Runtime 为恢复与审计保存的事实** 中分离出来。这不是对 Orchest 事件存储、compaction 或工具注册的替换。对使用者，目标是长任务跑到后半段仍能找回早先的关键证据，不必手工重发日志，也不必为一大段无关输入重复付费。对宿主，目标是知道本次用了哪些证据、遗漏的材料能否找回、什么时候省下的输入成本抵不过检索或判别的开销。

建议先在宿主示例中对 **长工具输出** 做小范围实验：同一个任务、同一个执行模型，对比现有历史与压缩、规则式片段选择、规则召回后接 Jev 重排。保持原始工具结果及其可授权读取的引用，选择结果只进入本次模型请求。验证有效后，再讨论是否有必要开放通用组装接口。工具搜索、模型切换、条件指令、子任务和后台评审分别验证，不作为首轮实验的前置。

## 1. 原文导读：它在问什么

[《Jev Engineering for Coding Agents》](https://jevforagents.com/media/Jev-Engineering-for-Coding-Agents.pdf) 是一份 2026 年 9 月的独立整理，基于 Diogo Almeida 的设计笔记，PDF 明示不代表 TypeSafe。它的思维实验是：如果不能依赖复用已经计算过的前缀，我们还会不会把模型输入设计成不断增长的对话？图 1 把系统分成可寻址状态、逐次小决策、上下文组装／路由、实际执行。Jev 在这里回答限定问题，生成模型和工具完成工作。

## 2. Orchest 已有能力与具体差距

| 领域 | 基线已具备 | 研究问题 |
| --- | --- | --- |
| 持久状态和请求 | Session log 可重建状态；run 启动后，模型调用从投影构造消息。`before_model` 每次从当前步快照生成临时消息，请求完成不把这些临时改写直接追加进耐久历史。 | 如何让保留的 tool output、工件与来源有稳定引用？被压缩的历史仍能否按新问题读取？这两个能力不能从「有 Session」直接推得。 |
| 实际调用取证 | 可选 Rust Session Evidence 默认关闭，挂载后默认元数据；支持观察 adapter 边界、尝试和压缩来源，证据写入尽力而为。 | 应用选择器的候选、规则版本和已选引用需要单独出处；是否记录内容独立授权。Adapter 观察不证明 provider 收到请求，也不是推理引擎 token 级训练记录。 |
| Compaction | 配置达到阈值才处理；近期消息保留，切分避免把工具调用与结果拆开。摘要是降低活动历史体积的现有机制。 | 按问题再读历史和流式控制预算是互补机制。摘要可作为导航，不能代替可核验源片段。 |
| 工具发现 | `ToolRegistry` 是能力注册面，`enable_tool_search()` 允许先发现再暴露完整 schema；已发现定义可追加给当前 run 后续调用。Skill 也已有渐进披露。 | 搜索质量、作用域和动态定义的生命周期是增量问题；不是再造工具发现，也不需要改变 MCP 作为传输的定义。 |
| 权限 | 宿主 `PermissionPolicy`、工具元数据及审批、guardrails、Draft/Commit 等已有边界。 | 输入出境与工具执行是不同决定；授权后的片段才能进入 ranker；ranker 的分数不覆盖任何执行权限。 |
| 类型化决策 | 有独立 `Decision` 协议，SDK 可用 `decide`，OpenRouter 的 Jev 是一个后端。它可以绕过 agent loop 调用，不必伪装成生成模型。 | 从受限候选中判别是否值得调用，何时拒答；把返回值映射为允许的候选 ID，不让它写入原始业务状态。 |
| 委派与控制流 | 现有 `AgentAsTool`、`ContextMode::Fresh/Fork`、supervision、run 级事件与观察。 | 用显式证据包构造子任务的 `Fresh` 输入；现有 `Fork` 是对照，不自动等价于最小授权。 |
| 测量 | 已有 tracing、TokenUsage 接口和 Briefing Desk Eval Lab 的评测先例。 | 选择器额外消耗、冷／暖缓存、证据命中、误选与取消延迟需单独报出；不新造计费含义。 |

### 2.1 不要把 hook 的能力说大

基线中的 `ModelHookContext` 带有 `model_spec`，但 `call_model_phase` 在该边界只消费改过的 `messages`；分发仍走运行配置和 `state.tool_defs`。因此可先用消息 hook 做选片试验，不能靠改这个字段宣布切换 adapter、缓存命名空间或调度工具已生效。若未来需要裁剪有效工具集合或选择 adapter，应设计相应明确的输入输出及重试／回退语义，不偷用调试 hook。

另外，`after_tool` 与 `after_model` 不是这个实验的等价入口：前者会改变模型看到的工具结果，后者改写将追加进历史的响应内容。首轮实验不在这些地方静默丢弃源证据。若源产物在宿主侧另有存储，其寿命、可用性和恢复语义也不因 hook 存在而自动成立。

### 2.2 分开四种状态

| 状态 | 作用 | 何时有资格改变它 |
| --- | --- | --- |
| 会话事实／已提交事件 | 重建会话、证明运行中发生了什么 | 现有 Session 事件与检查点契约 |
| 宿主工件与索引 | 定位日志、文件、diff、结构化结果；支持按租户和版本读取 | 宿主写入、保留与授权策略；不默认永久保留 |
| 本次模型输入 | 当前目标、活动约束、选中的证据及呈现形式 | 本次组装；下一轮可以不同 |
| 证据与诊断 | 解释为什么这样选择、实际交给 adapter 的是什么 | 按原可观测契约与 opt-in 收集，不反写会话事实 |

这里的「上下文」指模型请求的输入，不是 Session 的分叉，也不是 Multivac 产品级任务记录。历史里有某条消息，不代表它本轮可读；本轮取到了某份文档，也不等于可写进长期记忆或对外导出。

## 3. 上下文组装：先把日志做成能回看的材料

### 3.1 一个两轮例子

以真实形状的合成长日志为例：早期记录了测试命令、随机种子和环境；中间夹着几千行重复输出；末尾包含失败断言。日志被加入历史后，用户接连问：

1. 「这次测试为什么失败？」需要失败断言、对应堆栈与该次试验身份。
2. 「那刚才怎么复现？」需要实际执行命令、参数、环境，以及它属于同一次试验的佐证。

如果第二轮只有为第一问写的摘要，模型可能重猜命令。可寻址日志允许随问题切换输入，而不否定第一轮的结论。若原文已失效，应该说哪一项无法确认；不能用同名测试的另一轮输出补位。

```text
已提交的 Session ──► 本次会话投影 ───────────────┐
宿主保存的原工件 ──► 授权/版本检查 ─► 可选片段 ─┤
当前问题 + 明确约束 ─► 规则召回 ─► [可选重排] ──┤
                                                   ▼
                              固定部分 + 本次证据 → adapter
                                 │                  │
                   选择原因与出处（可选）       实际请求证据（可选）
```

### 3.2 工件怎样引用

候选来自宿主已经有权读取的记录。对第一版，每个候选只需携带以下含义，不需要先做通用向量库或引入新的持久 Session schema：

| 字段含义 | 示例 | 为什么需要 |
| --- | --- | --- |
| 对象及版本 | `run-17/test-output@digest` | 区分相似文件名、重试、重新生成后的同路径文件 |
| 来源和可解析定位 | 工具操作 ID、字节或行范围 | 允许复验；减少指向其他运行的误匹配 |
| 形态与费用 | 源片段／摘要／仅引用，估算 token | 规划预算；摘要不冒充原文 |
| 信任及访问范围 | 所属项目、授权策略、有效期 | 先约束能看和能发送，再做排名 |
| 关系 | 同一个工具交换、某条摘要的来源、被替代版本 | 防止残缺的消息序列和旧材料冒充最新版本 |

若提供原文分段读取能力，解析引用时再次检查权限、版本和偏移；合适的返回不是泛泛的「找不到」，而是明确区分不存在、已改变、已撤销、当前不可访问。不因插入失败自动放宽访问范围。诊断记录优先保存引用、结果和版本，不把日志原文变成指标标签。附带内容即使出现类似指令的文本，也只作为证据，不进入受信指令层。

### 3.3 选择而不是重写

先锁定必须生效的宿主规则、当前用户目标与合法的消息结构，再在预算内裁剪可选上下文。原文的多级可见性，对这里可以收敛为：不注入、注入引用、注入确定性原文片段、注入允许且预算内的全文。需要生成式摘要时，从这个流程之外开始对照，明确摘要来源和失真风险。

选择器可以返回候选 ID、呈现形态和排序分；宿主校验 ID 属于候选集、权限仍有效、预算未超标，最后组装。对合法工具调用／结果保持完整配对、正确的角色与顺序，必要时作为整体保留；不能为了缩短请求把一条工具结果伪装成用户说的话。第一版只裁已标记的长产物，保持不识别的消息、控制事实和回答目标不变。没有匹配时，保守地用规则选片或查指定原文；无权限或证据确实不存在时明确缺口。

## 4. 路由经济性：前缀、迁移、复核一起算

原文第 4 页用贵模型单跑和贵／便宜／贵三段跑作对照。它的价值在于把重新读入列为支出，不能把它简化成「便宜模型不值得路由」。运行中把大量资料带到轻模型，结果回来后又要在主模型重读和复核，即使生成单价更低，总成本也可能更高。反过来，一个可用少量证据独立解决的小任务，可能适合轻模型。

对 Orchest，可以按下式记录整个任务路径，而不把原文特定模型价格写成默认值：

```text
原路径 = 执行模型各次调用（未缓存输入 + 缓存读/写 + 输出）
候选路径 = 检索 + 重排 + 各个模型调用 + 回传后重读/复核 + 失败回退
```

用 provider 自己的 usage 分类换算，避免把已经包含在 input 的 cache token 再加一遍。对不返回 cache 或 usage 的 provider，不能记为零。价格目录、模型版本、费率时间和缓存口径随报告留存。对稳定请求前缀的支持以及工具 schema 序列化顺序按真实 provider 验证，不把逻辑消息顺序当成底层缓存命中的保证。比较至少包含冷缓存、稳定前缀暖缓存、动态内容变化三类；选择器结果复用和推理前缀命中是两套不同机制。

一个与原文无关的**假设算例**：若原路径每轮复用 16k 前缀，命中后的单位输入成本是假设未缓存的 10%，该部分相当于 1.6k 未缓存 token。重组以后如果 4k 都变成未缓存输入，仅这部分就贵 2.5 倍，还没算判别开销。若仍能复用 16k 的稳定前缀、只把昂贵的动态后缀从 8k 减到 4k，才腾出相当于 4k 未缓存输入的空间支付新开销。这个账用于决定测什么，不代表供应商报价或实际缓存机制。

**两条入场门槛：**

1. 先检查该证据与工具后续可能接触的数据能否发往目标 provider；先验文件分类只是风险提示，不是运行中放行后续结果的凭据。权限不明时不出境，也不为了省钱换到未授权端点。缓存也遵循相同边界，不能借缓存、摘要、日志或父子任务通信跨越项目权限。
2. 在授权的集合内，再以实际耗时、计费 token／金额和任务结果选择。本文不在 v1 试验自动换 adapter，尤其不在 provider 重试时把任务无提示改派给另一个模型。

## 5. 工具、技能、规则：三种装载方式，不混成一个注册表

### 5.1 工具披露

对不大的注册表，直接给完整 schema 通常比追加一次发现交互更简单。对 MCP 工具多、并且不同任务用到的能力差别大的宿主，先用现有 `search_tools`。先跑基线，再考虑：索引显示简短能力描述；候选缩到可比较范围；只给实际可执行候选的 schema；遇到低置信、不在列表或参数不合法，保留模型正常搜索／澄清路径。工具排序不执行工具，也不构造未经验证的参数。schema 版本、被暴露集合和模型实际调用分别记录。

按次撤下定义比按次添加更复杂。需要证明旧消息中的工具对和恢复中的调用还能按协议解释，未完成工具和重试不会突然失去 schema；注册、可见和可调用不能混为一谈。可以先试短期的子任务工具集合，再测当前 run 动态撤下是否值得，避免给「本轮工具没展示但猜名仍能执行」留下路径。任何新机制都要比较发现召回、误调用、额外往返和 prompt 缓存代价。

### 5.2 Skill 与条件指令

Skill 是既有标准下的按需知识包；长期约束则有不同生命周期。用一个工作树切换例子：先读 `ui/` 获得该路径的风格规则；进入其他目录后，只有仍适用的规则保持生效；压缩后再次进入 `ui/` 时，通过宿主判定重新装载该路径当前版本的规则。全局安全约束不受相关性打分影响；不要求所有风格指南都永久挤占每轮上下文。

如果未来扩展，自上而下应用：

- **始终生效的规则**由宿主确定、按既定优先级装载；不交给 Jev 决定要不要看。
- **条件性约束**按经授权的项目、路径、操作或显式模式匹配；真正操作前也要检查适用范围，不能只靠问题文本推测下一步会碰哪里。
- **参考和示例**可以进入同一选择器，允许摘要或省略；不因为内容看起来像 `AGENTS.md` 就获得更高指令权威。

原文提到条件激活、撤下行为和用有名字的外部状态辅助大模型；这些方向不需要改变 `SKILL.md` 标准。行为的注册／启用／停用若需要变成能力，应另行定义其权限、生命周期、撤销和恢复语义，不能让选中一个技能文本就隐式安装长期 hook。

### 5.3 候选内置工具如何取舍

原文最后列了一份工具候选（输入／输出压缩、结构化搜索与纲要、仓库探索和文件查找）。建议按**要解决的问题**读这些名字，而非列进 Orchest core 的依赖清单：

| 参考类别 | 原文例子 | 在 Orchest 中先问什么 |
| --- | --- | --- |
| 压缩日志与工具输出 | headroom、rtk | 长日志中实际命令、首个故障、最后的状态是否仍找得回？原文引用是否跨重试稳定？若缺证据，能否补读？ |
| 定位符号及结构 | ast-grep、ast-outline | 与基础文本搜索相比，多找回哪些证据？跨语言、不支持语法或解析失败时如何回退？ |
| 减少仓库探索开销 | fastcontext、fff | 适用范围内第一次和第二次查找各快多少？索引版本如何绑定工作树与权限？真实搜索结果是否随文件变化更新？ |

从示例工具或宿主集成比较质量、速度、冷启动、权限和维护成本；适合复用的才进默认配置。工具更容易发现，并不消除安装体积、宿主支持、隔离和升级责任。

## 6. 子任务、重开与后台复用

### 6.1 新上下文不等于丢任务历史

重开 agent run 时可以从当前任务目标、明确约束、待办及几个必要证据重新开始，而不用复制整个对话。应显式区分：

- **恢复原 Session**沿 Orchest 已有恢复合同；不要把重开新上下文伪装成原 run 继续。
- **同一 Runtime 里的委派**优先用 `AgentAsTool`／`ContextMode::Fresh` 构造小输入，结果包括结论、证据引用和未解决事项；把 `Fork` 作为复杂任务的对照。
- **跨 Runtime 交接**由消费方保留任务身份、授权和固定的证据视图。Orchest 的本地取证或一次 API 调用输入，不取代 Multivac 的 Task Trajectory，也不自动意味着接手模型能访问所有原材料。

### 6.2 一个可复现的后台用例

主任务提交改动后，评审、变更说明和回归建议都可能要读相同的差异。宿主可以为同一提交或工作树快照生成一份受限的材料目录，每个后台 worker 再按自己权限和目的读取子集。输出是独立审阅工件，不默认注入主模型，也不写回源文件。

共享的是**检索结果及其定位**，不必共享包含所有内容的模型 prompt，也不是所有只读 worker 之间的全局缓存。源快照变化、成员访问撤销、策略发生变化时，必须让旧材料失效或重新审查。拿过 `rev A` 的 review 不能当 `rev B` 的验收。

并行不能只靠提示词声明「只读」：以明确能力集合与宿主执行限制保证。不改变当前 runtime 并行工具的保守默认。若多个 worker 需要写同一工作树，选择宿主层的隔离、单写者或明确的合并控制，且每次真正写入仍走权限。语义判断可以提示两个子目标相似；真正防重复执行用租约／幂等键并结合目标身份、快照与有效状态，不能仅凭相似度吞掉不同工作。

## 7. 权限与对外发送

在调用链上分开检查四件事：

1. **能读吗？** 宿主为当前身份和任务生成可读候选，片段或摘要也不能脱离来源的授权。
2. **能给这个 ranker 吗？** 如果重排使用远端服务，检查查询本身和候选正文是否都允许发送；不行就用同边界内的规则方案，不预发正文再检查。
3. **能给执行模型吗？** 再检查实际模型、有效请求、工具结果及后续新增内容；外传限制不能由模型信心分解除。
4. **能执行吗？** 继续通过 `PermissionPolicy`／guardrail／审批和宿主实际限制。模型仅能建议请求核对或人工确认，不能改写拒绝条件，不能追加授权。

PDF 的可编程权限方向值得参考，但静态检查脚本或预测会访问哪些文件都只是辅助信号，不能替代文件系统、进程和网络的执行边界。缓存、错误信息、选择器调试记录和后台工件同样会持有敏感数据，需继承作用域、保留策略和撤销约束。

## 8. 最小实验：长工具结果的二次取证

### 8.1 实验对象与对照

在宿主控制的示例中演示，先用合成材料，不访问用户原始仓库日志，不配置真实密钥。单个样例可验证契约，不能据此估算整体收益。第一阶段用可控的 adapter、ranker 和日志夹具；第二阶段才在有授权的 provider 上跑实际请求、缓存和计费对照。

每个 case 冻结：任务与追问、语料／工件版本、运行／工具定义、执行模型／adapter、预算、可读与可外传范围、正确证据、验证器版本。对 A/B/C 使用相同数据和授权。允许按引用取原文的场景要为三组提供相同能力和预算；如果新增原文取回能力本身也要估计收益，则另开一个消融对照，不把取回收益算给 Jev。

| 组 | 请求策略 | 要回答的问题 |
| --- | --- | --- |
| A | 现有历史投影与 compaction，保留既定阈值和配置 | 不引入选择器时，长上下文能取回多少关键证据？ |
| B | 具名工件切片；按规则或关键词在相同候选池中选片，用同一预算组装 | 确定性方法能否解决大部分问题？ |
| C | 同 B 的候选、预算与回退；加一次类型化 ranker 重排或弃权 | 比 B 好多少，额外耗时和费用是否合理？ |

要回答「为何失败」时，验证器匹配第一条致因和运行身份，不接受仅复述最终退出码。要回答「怎样复现」时，匹配命令、随机种子、环境、来源范围；返回某个同名试验的命令判错。选择是否正确和最终回答是否正确分开记录。固定样例先通过已知正确／已知错误、缺失材料和权限禁读的验证器自测。

### 8.2 覆盖矩阵

| 用例 | 预期观察 |
| --- | --- |
| 失败原因 → 复现参数 | 两个问题各拿到相关片段，引用指向同一次执行；第二问不依赖第一问的摘要恰好保留参数。 |
| 排序打乱／加入相近的其他运行日志 | 必要的源片段不因排列或相似干扰被轻易替换；记录跨样例的命中，而非把单例稳定性猜成普遍规律。 |
| 缺失真正答案 | 不编精确命令；能读到合法原文时请求指定范围，否则明确缺什么。 |
| 工具调用与结果跨切分边界 | 出站请求的配对和顺序有效；用户目标、必须规则和不识别的事件照常保留。 |
| 项目 A、项目 B 各有同名工件／权限在期间撤销 | 不能通过重排、cache、按引用取原文或后台结果把 A 的内容带进 B；撤销后重新授权，旧选择不能绕过拒绝。 |
| 选择器超时、不可用或返回候选集合外的 ID | 受控回退到规则方案或现有有效历史；不尝试越权读取、不静默重写 Session，不反复调用。 |
| 执行模型因可重试失败再次调用 | 观察 hook 每次触发；输入事实未变且重新授权通过时，复用同一次选择；查询、候选版本、作用域或政策变化时不复用。 |
| 用户在排名时点 Stop | 与超时区分：取消后不为回退启动新模型调用；分别测取消到无工作时延、是否发生新 dispatch、以及远端请求是否可能已计费。 |
| 冷缓存、暖缓存、动态证据变化 | 分开计输入、输出、缓存读写与排名花费，记录真实可用的 usage；未知不写 0。 |

### 8.3 超时、Stop 与重试

源码基线中，`run_before_model` 串行 await hooks；`call_model_phase` 在重试循环内执行该 hook，之后才进入包围模型分发的取消选择。在 [hook runner](https://github.com/jianantian/orchest/blob/88ea29cd89ad5a89e7d09875327a1595530948dc/crates/orchest/src/hook/runner.rs#L82-L107) 这一段没有本地超时，不能据此推断整个系统没有外层取消，也不能宣称测到了 Stop 延迟。

因此先注入可控慢 ranker，用明确的本地 deadline 验证；有宿主取消信号时将其和 deadline 分开，必要时由宿主在起调用前再检查。选择器超时允许规则回退；显式 Stop 不允许继续。扔掉本地 future 也不保证上游停止或退款。若 hook 已证明无法满足取消要求，就不要把远程 ranker 上到默认热路径，应改由拥有取消语义的应用边界或可验证的新 runtime 接口承载。

同一 run 内可缓存一次已验证选择以避开相同 adapter 重试付费，键至少包括：查询、候选 ID 与版本、有效访问范围、策略和 ranker 版本、预算规则；读取缓存前再做授权检查。一次性诊断不跨 run、项目或用户共享。它不同于 provider 前缀缓存，也不是持久任务记忆。

### 8.4 指标、验收与停止条件

| 维度 | 记录 |
| --- | --- |
| 质量 | 必选源片段召回、错误源引用率、缺证据时的弃权／补读、最终 verified correctness；保留所有失败与未评分记录。 |
| 用户体验 | 首个可用输出、总完成延迟、P50/P95、额外往返、Stop 到静止。 |
| 经济性 | 实际 provider usage 和可得金额，含查询、召回后的生成、缓存、重试、规则回退；与预算估算对照。 |
| 完整性 | 规则与合法工具对不丢失；同一事实不因展示被重写；证据来源可解析且范围正确。 |
| 约束 | 数据越权出境、工具绕过与取消后的新分发是硬失败，不用平均质量或节省费用抵偿。 |

报告按 case 公开 A/B/C 结果、失败例及样本范围，避免只统计成功任务；缓存对比定序或交错执行以减少暖机偏差。在冻结样例上先通过质量与约束门槛，再用独立样例检验收益。C 不比 B 稳定更好，或者付出的端到端延迟与费用抵掉收益，就不引入远程重排；B 如也无明显收益，保留现有系统。第一版不设凭空的百分比目标，等小规模基线测量后再约定门槛。

与 [Briefing Desk Eval Lab 的先例](../review/v0_16_eval_lab.md) 相同，优先把 fixture、参照运行、grader 与证据区分。可以保留选择记录和验证结果做回归，不把日常生产轨迹、模型诊断或公开 benchmark 解答自动转成训练集。

## 9. 阶段与非目标

1. **现状量化。** 在不改 runtime 的示例中确定长日志用例与 verifier；测现有 compaction，记录真实漏证据的路径。
2. **测试选择。** 加入具名工件和规则选择；复用现有消息 hook 实施局部按请求组装，优先测不可用证据和权限；用 fake ranker 做取消／重试。
3. **比较远程重排。** 在被允许的数据上接现有 `Decision` 后端；比较 B/C，按真实 adapter / provider 口径测缓存、费用和延迟。不把某个供应商的名义价格或 benchmark 直接变成默认策略。
4. **必要时抽象。** 只有示例显示重复可复用需求时，才讨论正式 Context Assembly 接口：输入是已授权候选与活动约束，输出是明确作用域的一次调用计划及可审计引用；应用策略不进入 provider crates，也不进入 FFI。若需要变化的是工具可用性或 adapter 选择，另做设计，不把它们偷偷并入消息 hook。
5. **分别评估扩展。** 条件规则、短生命周期工具定义、对子任务分发小上下文、后台复用、模型路由，各有独立验收与成本，不用长日志实验代替。

**非目标：** 重写或废弃 Session v2、默认开启 raw evidence、自动分发给任何第三方模型、让 Jev 决定权限、全量替换 compaction、把原文列出的工具绑定为 Orchest core 依赖、调整 SDK 对外契约或把这项研究排进某个版本。没有发布、训练或迁移安排。

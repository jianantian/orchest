# 003 · 关联 adapter 返回、hook 和会话提交

GitHub issue: #360

## 背景

实时消息可以先于 `after_model` 展示，adapter 返回成功后仍可能被改写、被拒绝或因运行取消而未入账。

## 目标

在同一尝试下查询 adapter 的结算、有限的可观测输出信息、hook 结果和实际提交状态。复用 002 的采集与权限策略。依赖 002。

## 验收标准

- [ ] 成功返回且 hook 改写时，受控策略能区分返回内容和入账内容。普通文本和工具调用两条路径均使用 append 返回的实际 `SessionEvent.seq` 关联 `AssistantMessage`。在原有 checkpoint 确认耐久后，重读可验证该引用。
- [ ] 用 fixture 保留旧尝试证据、丢弃未落盘消息、恢复后复用同一序号。旧引用保持未确认。存在同序号、同事件种类甚至同正文的新事件时也不得重新认领；确认凭据只能来自原写入对应的成功耐久屏障。
- [ ] hook 拒绝、取消、异常 stop reason 和流失败均验证各自的结算；运行未追加消息时无入账引用。捕获的 adapter 流前缀带有不完整标记。进程中断或关联对象缺失时保留未知，宿主是否渲染过某个前缀需要宿主提供证据。
- [ ] 可控样本分别覆盖明确的本地拦截、有发送证据但缺少终态、发送未知。adapter 返回正常值、普通错误或流片段时仅更新 adapter 观察状态；在缺少 transport 或上游证据时发送状态保持未知。
- [ ] 分别显示 adapter 提议、hook 后入账的提议、v2 `ToolDispatched` 记录和结果。审批拒绝和派发前 checkpoint 失败各有样本。派发标记仅证明 v2 账本记录的阶段，恢复合成结果保持 v2 原义。流记录有界，慢写时原有 SDK 流、取消和重试规则仍按 v2 行为执行。

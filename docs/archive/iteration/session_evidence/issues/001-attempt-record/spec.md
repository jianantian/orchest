# 001 · 记录并读取逐次调用元数据

GitHub issue: #358

## 背景

现有运行时事件提供实时观察。Session v2 日志保存恢复事实。同一 step 的失败、取消和重试需要独立的历史标识。

## 目标

为 Rust 宿主提供显式启用的、按 Session 查询的本地尝试记录。每次调用以独立的 `attempt_id` 标识，携带 Session、run、step 和尝试序号。提供与实际 adapter 调用边界及已确认结算的关联。依赖 Session v2。

## 验收标准

- [ ] 同一步首次调用失败、随后重试成功，重开本地存储后可查到两次尝试及各自 provider、model 和结算。分别验证外部 resume 与沿用原 run id 的 Supervisor 重启，复用 step 时记录无覆盖或混淆。
- [ ] 两个 SessionStore 中的同名 Session、删除后重建的同名 Session 各自隔离。宿主可以清理相应证据。缺少 Session 绑定、策略或读取授权时，不能把证据附到其他会话。旧证据遇到未知 schema 时给出读取状态，原恢复路径可照常工作。
- [ ] hook 拒绝、上下文校验失败或已确认在调用前取消可显示本地决策；观察到 adapter 调用只证明到了本地边界。发送状态依据 transport 证据，缺失时为未知。
- [ ] 默认关闭时无证据写入。开启元数据模式时，原始消息、工具 schema、参数正文、错误原文和凭证均未进入证据存储。adapter 提供的任意错误字符串不能作为稳定分类直接存储。
- [ ] 写队列、单条记录、持久总量及读取窗口都有上限。阻塞写入端直至队列饱和时，模型流、checkpoint 和工具派发仍能按原路径完成。启用、禁用、损坏和丢失证据时，旧 v2 日志的恢复结果一致。
- [ ] 同一尝试记录按同一标识重复写入时查询结果无重复；先读到起始记录或结算记录其中之一时，另一项标为未知。可确认的缺口显式报告；整个尾部丢失且无额外证据时，查询结果不声称完整。
- [ ] 为后续消息和压缩引用提供共用的事件确认机制。使用 Session 事件 append、原 checkpoint 和读回事件验证三处事实；失败或丢失的确认不能由重读时遇到的同序号事件代替。

## 注记

首版没有 transport 证据的 adapter 保留发送状态未知。003 用可控样本验证有发送证据的状态。

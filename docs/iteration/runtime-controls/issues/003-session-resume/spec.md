# 003 · Session v2 配置与恢复

## 背景

Rust 已有 `SessionStore`、`AgentRun::resume` 与 `resume_with_input`。两个 SDK 都能传入历史消息来启动运行，但尚未暴露 Session v2 的本地存储和恢复。

## 目标与范围

通过显式选择的本地持久存储和 Session ID 暴露核心恢复能力。两端复用 001 的事件路径和 002 的运行控制。

同一 SQLite 存储、同一 Session ID 的 SDK 启动与恢复共用单写者规则。Rust 会话层在读取恢复快照或启动运行前取得写入权，持有至最终事件入账或运行失败退出。冲突可立即识别，持有者退出后可重试。首版覆盖使用该契约的 SDK 本地进程，直接写 SessionStore 的其他调用方需协调写入。

## 验收标准

- [ ] 宿主运行后关闭并重建实例，使用同一路径和 Session ID 可读取原会话状态。无新输入的恢复保留既有投影，追加新输入的恢复只记录一个新用户轮次。
- [ ] 缺失存储配置、未知会话和不可读存储返回可区分错误。旧入口在无存储时仍按原行为运行。
- [ ] 可控 fixture 在 checkpoint 处停止，恢复后历史与核心投影一致。副作用已提交、未知与未开始的情形沿用核心恢复规则。
- [ ] 共享测试验证两个不同本地存储中同名 Session 的隔离。恢复由宿主重新提供运行配置、adapter 和工具注册。
- [ ] 使用同一数据库的不同连接和两个宿主进程触发启动或恢复竞争。一个取得写入权，另一个得到类型化冲突错误。失败方不会调用模型、派发工具或写入会话。不同 Session 的运行可同时推进。
- [ ] 持有者正常退出、初始化失败或进程异常退出后，另一个宿主可重新取得写入权并按 Session v2 恢复。验证等待最终入账期间仍拒绝第二个写入方。

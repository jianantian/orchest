# 004 · 追踪压缩与已生效上下文

GitHub issue: #361

## 背景

现有 `Compacted { messages }` 保存有效替换。摘要调用有独立结果；现有实现允许 `before_compact` 修改工作消息，摘要失败后这些修改仍可能进入 `Compacted`。

## 目标

把压缩尝试与实际生效的 Session 事件、上下文版本和来源关联到可查询证据。依赖 002 的输入采集与读取，可独立于 003 的 assistant 返回和入账能力验收。

## 验收标准

- [ ] 成功压缩能查到触发原因、基线与替换后的投影、实际 `Compacted` 的事件序号、已知保留/替换来源和独立的摘要调用引用。摘要调用能按 002 的规则查询其实际输入。下一次主循环请求关联当时的基线和过 hook 后实际传入的上下文。
- [ ] 分别覆盖未触发压缩、进入压缩后跳过摘要、摘要取消、摘要失败。只在 `Compacted` 实际追加后推进替换，耐久状态取自原有 checkpoint。摘要失败或提前返回但 hook 改写实际提交时，读端能看到独立的压缩结算和替换事实。
- [ ] 两次压缩夹一次失败压缩仍能顺着引用追到已知的原生事件或前序摘要。覆盖同正文同角色、任意 hook 改写，以及两次调用间的 handoff。按实际 Session 前缀定位基线；无法逐条归因时标记未知。
- [ ] 模拟压缩时证据持久化失败，确认恢复仍使用原 `Compacted`，保留工具配对和原 checkpoint 行为。摘要调用证据的内容采集继续受 002 的策略约束。

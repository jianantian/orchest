## Critical（影响正确性或安全边界）

### C1. `agent-runtime-core` 反向依赖 `agent-runtime-providers`

**文件**：`crates/agent-runtime-core/Cargo.toml:19`，`crates/agent-runtime-core/src/model/mod.rs`

Core crate 通过 Cargo dependency + blanket re-export 依赖 providers crate 获取 `ModelAdapter` trait 和所有核心类型（`Message`、`ContentBlock`、`TokenUsage`、`StreamEvent` 等）。

**后果**：

- 编译 core 必须编译全部 4 个 provider adapter 实现（Anthropic 1600 行、OpenAI 816 行、DeepSeek 841 行、OpenRouter 887 行）
- 新增 provider 污染 core 编译图
- 类型来源语义错乱：`core::model::Message` 实际定义在 `providers::types.rs`

**建议**：抽取 `agent-runtime-model` crate，只含 trait + 纯数据类型。Core 和 providers 都依赖它。

### C2. Budget 检查丢弃违规原因

**文件**：`crates/agent-runtime-core/src/run/loop_.rs:147`

```rust
if let Some(_violation) = budget.check() {  // BudgetViolation 被丢弃
    emit(&tx, RuntimeEvent::RunFailed {
        error: "budget_exceeded".into(),     // 无法区分 token/cost/duration/tool_calls
    }).await;
}
```

`BudgetGuard::check()` 返回 `Option<BudgetViolation>` 枚举（4 个变体），但被 `_violation` 丢弃，`RunFailed.error` 只有通用字符串。

**建议**：`format!("budget_exceeded: {violation:?}")`。

### C3. `SkillEnvManager` 缺少显式 `Clone` derive

**文件**：`crates/agent-runtime-core/src/skill/mod.rs:129`，`bundled_tool.rs:405`

`SkillEnvManager` 不 derive `Clone`，但 `SkillBundledTool::clone_for_poll()` 调用 `self.env_manager.clone()`。当前因 `PathBuf` 是 field-wise `Clone` 的而编译通过，但依赖隐式行为——添加新字段（如 `Mutex`）会直接 break。

## High（影响可靠性或可维护性）

### H1. 无优雅取消机制

**文件**：`crates/agent-runtime-core/src/run/handle.rs`，`mod.rs`

`RunHandle` 暴露 `wait()` 但无法取消运行中的 agent。Drop event receiver 只能让 run loop 阻塞在 `tx.send().await`（channel 满后），不会终止。

**建议**：`tokio::sync::CancellationToken` 或 `watch` channel，循环顶部检查。

### H2. Node SDK 每次调用创建新 Tokio Runtime

**文件**：`crates/agent-runtime-node/src/lib.rs:325, 387, 422`

`run_sync()`、`run_stream()`、`respond_approval()` 各自 `Runtime::new()`，用完隐式 drop。浪费线程池初始化成本，增加延迟。

**建议**：`OnceLock<Runtime>` 或 `lazy_static` 共享。

### H3. Webhook Server 手动解析 HTTP

**文件**：`crates/agent-runtime-core/src/run/webhook.rs`

原始 TCP socket + 字符串匹配解析 HTTP（Content-Length 分片、header 解析、body 切分），不支持 chunked encoding / keep-alive。

**建议**：引入 `hyper`、`tiny_http`，或至少 `httparse`。

### H4. MCP HTTP Client JSON-RPC ID 硬编码为 `1`

**文件**：`crates/agent-runtime-core/src/tool/mcp.rs:350`

```rust
let body = json!({"jsonrpc": "2.0", "id": 1, ...});
```

Stdio client 用 `AtomicU64` 递增，HTTP client 硬编码 `1`。当前因串行调用而安全，但未来并发化会路由错误。

**建议**：对齐 stdio client。

### H5. Event Channel 容量 256 可能导致背压死锁

**文件**：`crates/agent-runtime-core/src/run/mod.rs:20`

```rust
let (event_tx, event_rx) = mpsc::channel(256);
```

消费者慢于生产者时 channel 填满，`tx.send().await` 阻塞 run loop 导致 token 超时。

**建议**：至少 `4096` 或 `unbounded` + 文档说明。

## Medium（改进建议）

### M1. `#[allow(clippy::result_large_err)]` 大量使用

`ModelError` 和 `ToolError` 各含 6-7 个字段，每个 `complete()` 和 `execute()` 方法都需 `#[allow(clippy::result_large_err)]`。热路径有栈复制成本。

**建议**：不常用字段（如 `upstream_body: Option<Value>`）放入 `Arc`。

### M2. `ToolContext` 应 derive `Clone`

**文件**：`crates/agent-runtime-core/src/tool/mod.rs:80-86`，`in_process.rs:64-70`

`InProcessTool::execute()` 手动逐字段复制 `ToolContext`。新增字段时容易遗漏。

**建议**：`#[derive(Clone)]` for `ToolContext`。

## 工程原则审查

按 SOLID、错误处理、并发、API 设计、安全、性能等业界原则逐项审查。与前面按模块的发现互补——这里聚焦**系统性模式**而非单点缺陷。

### P1. Provider 注册表违反开闭原则（Open/Closed）

**文件**：`providers/lib.rs:51-92`，`providers/lib.rs:109-127`

新增一个 provider 需要修改三处中央调度代码：

1. `create_adapter_from_config()` — 新增 match arm（4 个 arm，每增一个 provider +1）
2. `normalize_provider_model()` — 新增 `match provider { ... }` arm
3. `default_api_key_env()` — 新增 arm

且每个 arm 构造 `XxxConfig` 时**所有字段都相同**（`model`、`max_tokens`、`api_key`、`api_url`），只有 `OpenRouterConfig` 多了 `app_title`/`site_url`。应该使用 trait 对象注册表或 macro 消除重复。

**建议**：定义 `ProviderFactory` trait（`fn from_config(ProviderRuntimeConfig) -> Result<Box<dyn ModelAdapter>>`），各 adapter 实现，用一个 `HashMap<&str, Box<dyn ProviderFactory>>` 注册表替代 match。

### P2. 审批等待无超时（并发安全）

**文件**：`run/loop_.rs:321`

```rust
let approved = approval_rx.await.unwrap_or(false);
```

`oneshot::Receiver::await` 没有 `.timeout()` 包装。如果调用方忘记（或无法）调用 `respond_approval()`，run loop **永久挂起**。这是无取消机制（H1）在审批路径的具体表现。

**建议**：`tokio::time::timeout(APPROVAL_TIMEOUT, approval_rx).await`，超时视为拒绝。

### P3. `ToolError` 无法包装底层错误（错误链断裂）

**文件**：`tool/mod.rs:95-99`

```rust
pub struct ToolError {
    pub message: String,
    pub code: Option<String>,
}
```

`ToolError` 只有 `message` + `code`，没有 `source: Option<Box<dyn Error>>`。当 `McpTool::execute()` 返回 `McpError` 时，`impl From<McpError> for ToolError`（`mcp.rs:49-55`）丢弃了原始错误的 `code` 字段，只保留 `message`：

```rust
impl From<McpError> for ToolError {
    fn from(value: McpError) -> Self {
        Self { message: value.message, code: value.code }  // ← McpError 的类型信息丢失
    }
}
```

调用方无法通过 `error.source()` 追溯根因。整个代码库的错误类型都是平铺的——`ModelError`、`McpError`、`ScriptError`、`ToolError` 之间互相转换时丢失类型信息。

**建议**：所有 Error 类型实现 `std::error::Error` 的 `source()` 方法，转换时保留原始错误。

### P4. `AgentConfig::builder().build()` 无校验（API 契约）

`AgentConfigBuilder::build()` 总是返回 `AgentConfig`，从不返回 `Result`。以下配置会静默产生无意义运行：

- `system_prompt: ""` — agent 无系统指令
- `model.spec.model: ""` — 空模型名
- `budget.max_cost_usd: Some(-1.0)` — 负成本（`f64` 不阻止）
- `runtime.max_steps: 0` — 一步都不跑

所有校验推迟到运行时（`create_adapter` 才发现空 model、`loop_.rs` 才检查 `max_steps`）。

**建议**：`build() -> Result<AgentConfig, ConfigError>`，在构建时校验 `model` 非空、`system_prompt` 非空、`max_cost_usd >= 0.0`。

### P5. `ReadFileTool` 无路径沙箱（安全）

**文件**：`tool/builtin.rs:139-142`

```rust
let path = PathBuf::from(path_str);
let content = tokio::fs::read_to_string(&path).await...;
```

模型可以读取任意文件系统路径。无白名单、无根目录限制、无符号链接检测。一个 `read_file("../.env")` 就能泄露密钥。

**建议**：增加 `allowed_roots: Vec<PathBuf>` 配置，拒绝 root 外的路径。`SkillBundledTool` 已有 `script_resolved.starts_with(&skill_dir_resolved)` 保护，`ReadFileTool` 应同级实现。

### P6. `ExecutePythonTool` 继承完整父进程环境变量（安全）

**文件**：`tool/code_exec.rs:212-217`

```rust
let mut child = Command::new("python3")
    .arg("-u").arg("-i").arg("-q")
    .stdin(Stdio::piped())
    .stdout(Stdio::piped())
    .stderr(Stdio::null())
    .spawn()...;
```

不调用 `.env_clear()`。子进程继承 `PATH`、`HOME`、`AWS_*`、`DATABASE_URL` 等全部环境变量。对比 `SkillBundledTool` 的 `BareSubprocessExecutor`——它执行 `.env_clear().envs(&ctx.env)`（`executor.rs:94-95`）。

### P7. `PythonSession` 退出后残留死 session（资源泄漏）

**文件**：`tool/code_exec.rs:101-104`，`execute_python_in_session`

Python 子进程退出（EOF）时，`read_line` 返回 0 bytes，函数返回 `SESSION_EXITED` 错误。但 `session: Arc<Mutex<Option<PythonSession>>>` **未被置为 `None`**——只有超时路径（line 102-103）才 `session.take()` 并 kill。正常退出后下次调用 `execute_python_in_session` 会检测到 `guard.is_some()` 而跳过重建，再次读取到 EOF，再次报错。死循环。

**建议**：收到 EOF 时也 `session.take()` 清理。

### P8. `ToolRegistry::list()` 每次分配（热路径）

**文件**：`tool/registry.rs:31-42`

```rust
pub fn list(&self) -> Vec<ToolDef> {
    self.order.iter()
        .filter_map(|name| {
            let tool = self.tools.get(name)?;
            Some(ToolDef { name: tool.name().to_string(), ... })
        })
        .collect()
}
```

每个 model turn → `run_loop` → `registry.list()` 调用一次。对 N 个 tool，每次分配 N 个 `ToolDef` + N 个 `String`。`ToolDef` 本身是轻量的（3 个字段），但 N=500 时每步 500 次小分配。

**建议**：缓存 `Vec<ToolDef>`，注册/注销时 invalidate。或者直接存 `Vec<Arc<ToolDef>>` 而非每次重建。

### P9. `json!()` 宏在请求构建热路径分配密集

**文件**：四个 adapter 的 `build_request_body()`

每个 message 的每个 content block 都调用 `json!()`——这个宏内部创建 `serde_json::Value` 树，涉及大量 `Map` 和 `Vec` 分配。对于 100 条消息的对话，单次 `build_request_body` 分配数千个临时 `Value`。

**建议**：用 `serde::Serialize` + `serde_json::to_value` 批量序列化，减少中间分配。或预分配 `Vec<Value>` 容量。

### P10. `record_model_success()` 参数爆炸（可维护性）

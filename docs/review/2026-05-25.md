## Bugs（行为正确性缺陷）

### B1. Budget 检查丢弃违规原因

**文件**：`crates/agent-runtime-core/src/run/loop_.rs:147`

```rust
if let Some(_violation) = budget.check() {  // BudgetViolation 被丢弃
    emit(&tx, RuntimeEvent::RunFailed {
        error: "budget_exceeded".into(),
    }).await;
}
```

`BudgetGuard::check()` 返回 `Option<BudgetViolation>`（4 个变体），被丢弃。调试时无法区分 token/cost/duration/tool_calls。

### B2. 审批等待无超时 → run loop 永久挂起

**文件**：`run/loop_.rs:321`

```rust
let approved = approval_rx.await.unwrap_or(false);
```

`oneshot::Receiver` 无限等待。调用方忘记调用 `respond_approval()` 时 run loop 永久挂起。

**建议**：`tokio::time::timeout(APPROVAL_TIMEOUT, approval_rx).await`。

### B3. `PythonSession` 正常退出后死循环

**文件**：`tool/code_exec.rs:101-104`，`execute_python_in_session`

Python 子进程 EOF 时函数返回 `SESSION_EXITED` 错误，但 `session` 未置 `None`（只有超时路径才 `take()`）。下次调用检测到 `is_some()` 跳过重建，再次 EOF，死循环。

**建议**：EOF 路径也 `session.take()`。

## Security（安全边界）

### S1. `ExecutePythonTool` 继承完整父进程环境变量

**文件**：`tool/code_exec.rs:212-217`

`Command::new("python3")` 不调用 `.env_clear()`，子进程继承 `PATH`、`HOME`、`AWS_*` 等。对比 `BareSubprocessExecutor` 的 `.env_clear().envs(&ctx.env)`。这不是沙箱缺失——沙箱是明确 non-goal。这是同一代码库内两个 executor 的安全模型不一致。

详见 [`docs/polaris/sandbox-gap-analysis.md`](../polaris/sandbox-gap-analysis.md)。

## Architecture（结构债务）

### A1. `agent-runtime-core` 反向依赖 `agent-runtime-providers`

**文件**：`Cargo.toml:19`，`model/mod.rs`

Core 通过 Cargo dependency + 27 符号 blanket re-export 获取 `ModelAdapter` trait 和核心类型。后果：编译 core 必须编译全部 4 个 adapter；新增 provider 污染 core 编译图。

**建议**：抽取 `agent-runtime-model` crate，只含 trait + 纯数据类型。

### A2. Provider 注册表违反开闭原则

**文件**：`providers/lib.rs:51-92`

新增 provider 需修改三处 match：`create_adapter_from_config`、`normalize_provider_model`、`default_api_key_env`。每个 arm 构造 `XxxConfig` 字段完全相同。

**建议**：`ProviderFactory` trait + `HashMap` 注册表替代 match。

### A3. OpenAI 兼容 adapter 消息序列化逐字重复（~210 行）

**文件**：`openai.rs`、`deepseek.rs`、`openrouter.rs`

`Role::System`、`Role::User`、`Role::Tool` 分支逐行相同。四个 `complete()` 后半段（错误处理 → usage 检查 → Done → telemetry）另有 ~240 行重复。

**建议**：`OpenAiCompatibleMessageBuilder` + 差异 hook。

### A4. 文件 / 函数超长

| 项目 | 最严重 | 行数 |
|------|--------|------|
| 文件 | `provider/anthropic.rs` | 1,603 (4.0× 约定) |
| 函数 | `AnthropicAdapter::complete()` | 363 |
| 函数 | `parse_openai_sse_stream()` | 311 |

AGENTS.md 约定 400 行/文件。11 个文件超标。

### A5. `mod.rs` 含业务逻辑

`tool/mod.rs`（111 行）含 `Tool` trait + 全部关联类型；`skill/mod.rs`（604 行）含 4 个 struct + scanner。`model/mod.rs` 是 27 符号 blanket re-export。

### A6. `ToolError` 错误链断裂

`ToolError` 只有 `message` + `code`，无 `source`。`From<McpError>` 转换丢弃原始 `code`。`ModelError`、`McpError`、`ScriptError`、`ToolError` 之间转换丢失类型信息。

**建议**：所有 Error 实现 `std::error::Error::source()`。

### A7. `AgentConfigBuilder::build()` 无校验

`build()` 永远返回 `AgentConfig`。空 `system_prompt`、空 `model`、负 `max_cost_usd`、`max_steps: 0` 全部静默接受，推迟到运行时才发现。

**建议**：`build() -> Result<AgentConfig, ConfigError>`。

### A8. `record_model_success()` 参数爆炸

7 个位置参数，4 个调用点。新增字段需改签名 + 全部调用点。

**建议**：参数结构体。

### A9. Webhook Server 手动解析 HTTP

**文件**：`run/webhook.rs`

原始 TCP socket + 字符串匹配，不支持 chunked / keep-alive。

### A10. Event Channel 容量 256

消费者慢时 channel 填满，`tx.send().await` 阻塞 run loop。

**建议**：至少 4096 或 unbounded。

### A11. `SkillScanner` 阻塞 I/O 未包裹 `spawn_blocking`

`scan_recursive()` 调用 `std::fs::read_dir()`，`parse_skill_md()` 调用 `std::fs::read_to_string()`，被 async `register_skills()` 同步调用。影响小（仅启动时执行一次），但违反 convention。

### A12. `ToolContext` 手动逐字段复制

`InProcessTool::execute()` 逐字段 clone `ToolContext`。新增字段容易遗漏。

**建议**：`#[derive(Clone)]`。

### A13. `#[allow(clippy::result_large_err)]` 大量使用

`ModelError` / `ToolError` 各 6-7 字段，每个方法需 suppress clippy。

**建议**：大字段（`upstream_body`）入 `Arc`。


### A14. `SkillEnvManager` 缺少显式 `Clone` derive

**文件**：`skill/mod.rs:129`，`bundled_tool.rs:405`

`SkillBundledTool::clone_for_poll()` 调用 `self.env_manager.clone()`，但 `SkillEnvManager` 不 derive `Clone`。当前因唯一字段 `PathBuf` 是 `Clone` 的而编译通过，依赖隐式行为——加 `Mutex` 字段直接 break。

### A15. MCP HTTP Client JSON-RPC ID 硬编码为 `1`

**文件**：`tool/mcp.rs:350`

```rust
let body = json!({"jsonrpc": "2.0", "id": 1, ...});
```

Stdio client 用 `AtomicU64` 递增，HTTP client 硬编码 `1`。当前串行安全，并发化后响应路由错乱。

**建议**：`OnceLock<Runtime>`。

## Lint 与 CI 防线

以下配置在本轮修复完成后落地，防止回归：

### `clippy.toml`（新建）

```toml
too-many-lines-threshold = 200
too-many-arguments-threshold = 5
```

### `Cargo.toml` workspace lint

```toml
[workspace.lints.clippy]
too_many_lines = "warn"
too_many_arguments = "warn"
result_large_err = "warn"
```

### CI 脚本检查（补充 clippy 覆盖不到的项）

```bash
# 文件超长检查（排除 tests.rs）
echo "--- Files exceeding 400 lines ---"
find crates/ -name '*.rs' ! -name 'tests.rs' ! -path '*/target/*' \
  | xargs wc -l | awk '$1 > 400 {print}' | grep -v total

# mod.rs 业务逻辑检查（mod.rs 不应超过 50 行）
echo "--- mod.rs files exceeding 50 lines ---"
find crates/ -name 'mod.rs' ! -path '*/target/*' \
  | xargs wc -l | awk '$1 > 50 {print}' | grep -v total

# async 代码中的阻塞 I/O 检查
echo "--- std::fs in non-test async code ---"
grep -rn 'std::fs::' crates/ --include='*.rs' | grep -v '/tests' | grep -v 'test_' | grep -v '#\[cfg(test)\]'

# clippy allow 残留检查（修复后不应再有）
echo "--- Remaining clippy allows ---"
grep -rn '#\[allow(clippy::' crates/ --include='*.rs' | grep -v '/target/'
```

这些检查加入 CI pipeline，与现有 `cargo clippy -- -D warnings` 并行执行。文件/函数超长和 mod.rs 逻辑外溢是 clippy 管不了的，靠脚本卡住。`std::fs` 和 clippy allow 残留是修复后的回归防线。
